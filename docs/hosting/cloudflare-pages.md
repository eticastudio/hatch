# Deploy Hatch to Cloudflare Pages

> **[← Back to README](../../README.md)**

This is the **recommended path** for most Hatch users. Cloudflare Pages is free for the volumes most blogs see, runs on the global edge network, and integrates with Git so deploys are automatic.

**Time to live site: ~10 minutes** (most of it waiting for Cloudflare's build).

---

## Before you start

You should already have:

- ✅ Hatch installed on your WordPress (Tools → Hatch → Connector says "Connected" or the wizard completed)
- ✅ The `.env` block copied to clipboard (from Tools → Hatch → Connector)
- ✅ A GitHub account
- ✅ A Cloudflare account (free)

If you don't have the `.env` block yet, complete the setup wizard first (Tools → Hatch → "Run setup wizard").

---

## The full flow at a glance

```
1. Fork the Hatch repo on GitHub                       (1 min)
2. Cloudflare Pages → Connect to Git → pick your fork  (2 min)
3. Set build settings: directory + command + output    (1 min)
4. Add 4 environment variables                         (2 min)
5. Cloudflare builds + deploys                         (~3 min)
6. Visit your *.pages.dev URL — site is live           (done)
7. (Optional) Add your custom domain                   (5 min)
```

---

## Step 1 — Fork the Hatch repo

1. Go to **[github.com/adityaarsharma/hatch](https://github.com/adityaarsharma/hatch)**
2. Click **Fork** (top right)
3. Name it whatever you want, e.g. `my-hatch-site`

You'll deploy from your fork so you can edit theme code and have changes auto-deploy.

> If you don't want to fork — you can also clone the repo to a new private repo. The important part is that Cloudflare can read the `astro-starter/` directory from a Git repo you control.

---

## Step 2 — Connect Cloudflare Pages

1. Go to **[dash.cloudflare.com](https://dash.cloudflare.com)** → **Workers & Pages**
2. Click **Create** → **Pages** tab → **Connect to Git**
3. Authorize Cloudflare to access your GitHub
4. Pick your forked repo (`my-hatch-site`)
5. Branch: `main`

> If you see `*.workers.dev` URLs in your Cloudflare dashboard — those are Workers, not Pages. **For Hatch, use Pages.** Click "Create" → "Pages" tab specifically.

---

## Step 3 — Build settings

This is the critical part. Cloudflare needs to know the Astro starter lives in a subfolder.

| Setting | Value |
|---|---|
| **Production branch** | `main` |
| **Framework preset** | `Astro` |
| **Build command** | `npm install && npm run build` |
| **Build output directory** | `dist` |
| **Root directory** | `astro-starter` ← important! |

The "Root directory" tells Cloudflare to `cd astro-starter` before running the build — because the Astro project lives there, not at the repo root.

---

## Step 4 — Environment variables

Click **Environment variables** in the Pages settings. Add the 4 from your Hatch `.env` block:

| Variable | Value | Where it comes from |
|---|---|---|
| `HATCH_WP_URL` | `https://cms.yoursite.com` | Your WordPress URL |
| `WORDPRESS_USER` | `your-admin-username` | The WP user you generated the App Password for |
| `WORDPRESS_APP_PASSWORD` | `abcd efgh ijkl mnop ...` | Generated from Tools → Hatch → Connector → "Generate Application Password" |
| `HATCH_WEBHOOK_SECRET` | `(48-char string)` | Auto-generated by Hatch on activation |

**Also add** `NODE_VERSION` with value `22`.

**Important:** mark `WORDPRESS_APP_PASSWORD` and `HATCH_WEBHOOK_SECRET` as **encrypted** (Cloudflare hides them after save).

---

## Step 5 — Deploy

1. Click **Save and Deploy**
2. Cloudflare clones your repo, runs `npm install && npm run build` in `astro-starter/`
3. Wait ~2–3 minutes for the first build (subsequent builds are faster, ~30s)
4. When done, you'll see `your-project.pages.dev` URL

Open it. You should see your site — pulling posts from your WordPress CMS.

---

## Step 6 — Hook up revalidation (auto-rebuild on post update)

Right now Cloudflare rebuilds when you push to Git. Let's also rebuild when you publish a WordPress post.

### 6a — Create a Cloudflare Pages Deploy Hook

1. In Cloudflare Pages → your project → **Settings → Builds & deployments**
2. Scroll to **Deploy Hooks** → **Add Deploy Hook**
3. Name it: `Hatch revalidate`
4. Branch: `main`
5. Click **Save**
6. Copy the deploy hook URL (looks like `https://api.cloudflare.com/client/v4/pages/webhooks/deploy_hooks/...`)

### 6b — Tell Hatch about it

1. WordPress → **Tools → Hatch → Connector**
2. **Your Headless Website URL** field → paste the **deploy hook URL** (not your `.pages.dev` URL — the actual hook URL)
3. Click **Connect Hatch**

Now: when you publish a post in WordPress, Hatch POSTs to that deploy hook → Cloudflare rebuilds → site updates within ~2 minutes.

> Why a deploy hook instead of `/api/revalidate`? Astro on Cloudflare Pages is statically generated by default — there's no per-page revalidation endpoint. Triggering a full rebuild is the simplest model.

---

## Step 7 — (Optional) Custom domain

1. Cloudflare Pages → your project → **Custom domains** → **Set up a custom domain**
2. Enter `yoursite.com` (or `www.yoursite.com`)
3. Cloudflare auto-configures DNS if your domain is on Cloudflare DNS
4. SSL certificate is auto-issued (free, ~1 minute)

After this:
- Your **public site**: `https://yoursite.com`
- Your **WordPress backend**: `https://cms.yoursite.com` (where Hatch is installed)

---

## Verification checklist

After deploy, verify:

- [ ] `https://your-project.pages.dev` (or your custom domain) loads the home page
- [ ] `https://your-project.pages.dev/blog` shows your posts (if you have any)
- [ ] Open a single post — content loads, breadcrumb shows, reading time displays
- [ ] Publish a draft post in WordPress → wait 2 minutes → refresh frontend → new post appears
- [ ] Check Cloudflare → Pages → your project → Deployments tab → latest deploy should show 200

## Common issues

### "Build failed: cannot find directory `astro-starter`"

You forgot to set **Root directory** to `astro-starter`. Fix in Settings → Builds & deployments.

### "Build failed: 401 Unauthorized fetching `/wp-json/`"

Your `WORDPRESS_APP_PASSWORD` is wrong, expired, or mistyped. Regenerate it from WordPress (Users → Profile → Application Passwords) and update the env var in Cloudflare Pages settings.

### "Build succeeds but posts don't show"

Check that `HATCH_WP_URL` points to your CMS subdomain (e.g. `https://cms.yoursite.com`), not your frontend domain.

### "Posts appear but with broken images"

WordPress is serving images from `cms.yoursite.com/wp-content/uploads/*`. The frontend just embeds those URLs. Make sure your CMS is publicly reachable for media (Hatch's REST hardening blocks `/wp-json/*` but `/wp-content/*` stays public).

### "Webhook fires but site doesn't update"

1. Verify the deploy hook URL in Hatch matches the one in Cloudflare Pages
2. Check Cloudflare Pages → Deployments — did a new build start?
3. If yes → wait for it to complete
4. If no → the hook URL is wrong or Cloudflare's API rejected it. Regenerate.

### "I changed an env var but nothing happened"

Cloudflare Pages env vars apply on the NEXT build. Trigger a rebuild from Cloudflare Pages → Deployments → "Retry deployment", or push any change to your repo.

### "I see `plain-block-e9d4.workers.dev` in my dashboard"

That's a Cloudflare Workers default — different product. For Hatch, you want **Pages**, not Workers. Go back to Workers & Pages → **Pages** tab → Create.

## Don't want to fork? Three other paths

The fork approach is the most beginner-friendly because Cloudflare handles ongoing rebuilds automatically. But it's not your only option.

### Option B — "Use this template" (cleaner than fork)

If you don't want a literal fork relationship with the upstream Hatch repo:

1. Go to **[github.com/adityaarsharma/hatch](https://github.com/adityaarsharma/hatch)**
2. Click **Use this template** → **Create a new repository**
3. The new repo is yours, no fork relationship — no "Sync fork" button cluttering your repo
4. Connect Cloudflare Pages to your new repo (Step 2 of the main guide above)

Identical UX after that, just cleaner GitHub history.

### Option C — Wrangler CLI from terminal (no GitHub at all)

For developers who already have Node.js + terminal access. Zero GitHub required:

```bash
# 1. Clone (no fork — just read)
git clone --depth=1 https://github.com/adityaarsharma/hatch.git
cd hatch/astro-starter

# 2. Set env vars
cp .env.example .env
# Edit .env with values from Tools → Hatch → Connector

# 3. Install + build
npm install
npm run build

# 4. Install Wrangler if you don't have it
npm install -g wrangler

# 5. Authenticate (one-time browser auth)
wrangler login

# 6. Deploy
wrangler pages deploy dist --project-name=my-hatch-site
```

Cloudflare auto-creates the Pages project on first deploy. You get a `*.pages.dev` URL printed in the terminal.

**Re-deploy later** with the same command — Wrangler uploads only the changed files.

**Tradeoff:** no auto-rebuild on Git push. Either:
- Re-run `wrangler pages deploy dist` manually after content changes, OR
- Set up a Cloudflare Deploy Hook (Step 6 of the main guide) and point Hatch's webhook at it. Cloudflare will skip the build phase since you're using Direct Upload — it just serves the existing `dist/`.

**Better alternative for terminal users:** use GitHub Actions to build + deploy on a schedule or webhook. See `docs/hosting/cloudflare-pages-ci.md` (coming V0.7).

### Option D — Direct Upload via Cloudflare dashboard (drag and drop)

For folks who don't want Git OR Wrangler:

1. Locally: `git clone https://github.com/adityaarsharma/hatch.git && cd hatch/astro-starter && cp .env.example .env`
2. Fill in `.env` with values from your Hatch Connector tab
3. `npm install && npm run build` (still needs Node locally)
4. Cloudflare Pages → Create → Pages → **Upload assets** tab (instead of "Connect to Git")
5. Drag the `dist/` folder into the upload area
6. Cloudflare serves it — done

**Tradeoff:** you re-upload manually every time you want to deploy changes. Fine for "deploy once, forget" sites; tedious for active blogs.

### What about a button in WordPress that deploys for me?

Honest answer: **not yet, but it's on the roadmap.**

The technical version: WordPress could POST to the Cloudflare API on your behalf if you provided a CF API token. That would let the plugin create a Pages project, upload the pre-built `dist/`, and configure env vars — all without you touching Cloudflare's dashboard.

What blocks this today:
1. The Astro build has to happen *somewhere* with Node.js. PHP can't build an Astro site. Options:
   - Build on a third-party CI runner (GitHub Actions free tier — viable but requires GitHub anyway)
   - Build on a Cloudflare Worker (their build environment — Cloudflare does this for us when we use Git or Wrangler)
   - Build on a Hatch-hosted service (would require us to run infrastructure — V2.5+ Hatch Cloud)
2. Storing your Cloudflare API token in WordPress means another secret to encrypt + protect.

The realistic path: V0.7 ships a "Deploy to Cloudflare" button in the Connector tab that uses **GitHub Actions** as the build runner (so it's free, no Hatch infrastructure needed) and Cloudflare's API for the actual deploy. You'd connect both your GitHub + Cloudflare via OAuth once, then click one button forever after.

For v0.6, the realistic options are A/B (fork or use-template + auto-deploy) or C (wrangler CLI from terminal).

## Workers vs Pages — when to use which

You probably saw both options in Cloudflare's dashboard. Here's the difference:

| | Cloudflare Pages | Cloudflare Workers |
|---|---|---|
| Use case | Static sites + light dynamic | Full server-side compute |
| Build model | Git-connected, automatic | wrangler CLI deploys |
| For Astro static | ✅ Native | ⚠️ Requires adapter setup |
| Free tier | Unlimited bandwidth, 500 builds/mo | 100k requests/day |
| Hatch recommendation | ✅ Default | Advanced only |

**For 95% of Hatch users, use Pages.** Workers is for advanced setups where you need on-demand rendering / ISR-like behavior.
